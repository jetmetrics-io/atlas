# Правила работы в репозитории Атласа

Читается агентом при работе в этом репозитории. Подробности для человека —
[DEPLOY.md](DEPLOY.md), его стоит открыть перед любой задачей про данные или деплой.

## Главное правило

**Источник правды — База.** Это `db/atlas.sql` (дамп в git) и собираемая из него
`db/atlas.db`. Всё остальное — производные: выгрузка `public/data/*.json`, стенд,
бой на бакете.

⛔ **Никогда не правь выгрузку.** Ни `public/data/*.json`, ни `dist/data/*.json`,
ни файлами правок поверх. Правка, внесённая мимо Базы, живёт до следующей сборки
и разводит версии.

Так уже было 22.09.2026: переименование метрики применили к выгрузке, оно попало
в полную версию и не попало в бесплатную. Сутки неоплатившие видели одно имя,
оплатившие другое. Нашлось случайно.

## Как сделать правку данных

```sh
git pull && npm run db          # свежая База из дампа
# правка: миграция в db/migrations/ по образцу соседних
python3 db/migrations/00N_imya.py db/atlas.db
npm run db:check                # целостность
npm run gen                     # пересобрать выгрузку
npm run db:dump                 # База → дамп
git add db/atlas.sql db/migrations/ && git commit && git push
```

У миграции есть `primenit()`, `proverit()` и ключ `--check`; она делает бэкап
и переживает повторный запуск. Миграция — это ещё и объяснение, **почему** правка
такая: через месяц это единственное, что останется.

## Как выложить в бой

```sh
npm run pull      # что сейчас в бою и чем отличается от моего — СНАЧАЛА ЭТО
npm run deploy    # проверка, слепок для отката, сборка, выкладка
```

`npm run deploy` сам остановится, если из боя пропадают метрики или артефакты.
Остановился — не обходи ключом `--yes`, пока не понял, почему он против.

Откат: `npm run deploy -- --rollback .rollback`.

## Чего не делать

| ⛔ | Почему |
|---|---|
| Править `public/data/*.json` руками | правка не доедет до Базы и разведёт версии |
| Добавлять метрику прямо в выгрузку | `metric.id` — PRIMARY KEY только в Базе; в JSON ничто не помешает занять чужой id |
| Класть `db/atlas.db` в git | двоичный файл молча затирает чужую работу при слиянии |
| Ссылаться из кода на папки вне репозитория | `../content/`, `../../../dashboards-methodology/` — сборка сломается у всех, у кого их нет. Именно так CI падал 18 раз подряд |
| Коммитить `.deploy.env` | это боевые ключи от бакета |
| Выкладывать `payment/paid.json` | это список покупателей, его ведёт сайт |
| Заводить механизм «правок поверх выгрузки» | уже пробовали, см. главное правило |

## Две машины

Репозиторий общий: Дмитрий и Мария работают параллельно. Поэтому:

1. Перед правкой — `git pull` и `npm run db`, иначе правится вчерашняя База.
2. После правки — `npm run db:dump`, коммит и `git push` сразу, не копить.
3. Конфликт в `db/atlas.sql` не разрешается силой: ни `--ours`, ни `--theirs`.
   Обе стороны — чья-то работа. Сначала разговор.
4. Перед деплоем — `npm run pull`. Если бой ушёл вперёд, разберись, чей он.

## Правила контента

Как заполнять карточку метрики, что такое разрез, какие бывают артефакты —
репозиторий [`site-state`](https://github.com/jetmetrics-io/site-state), папка `atlas/`:
`RULES.md` (карточка, 15 полей), `ATLAS_DB.md` (устройство Базы),
`артефакты.md` (реестр карт и деревьев), `разрезы.md` (справочник разрезов).
Правила методологии — репозиторий `methodology`. Свои определения не сочинять.

## Если сборщик пришлось менять

`scripts/build_app.py` воспроизводит боевую выгрузку точно: сверен по 949 узлам,
974 связям и 949 карточкам. В его шапке описаны семь правил, которых нет в самой
Базе, — порядок записей, `style` по умолчанию, склейка формулы, `parent` и `total`
у деревьев. Меняешь любое — сверь результат с боем заново:

```sh
npm run gen && npm run pull
```
